## Objective

Make independently derived, reviewed canonical bytes the authoritative oracle
for CASM output and for every CASM-native external application. ca65 remains an
optional differential implementation for source that happens to remain inside
the shared subset; it no longer defines CASM language maturity, limits native
application syntax, supplies shipping bytes, or gates correctness outside that
intersection.

This effort formalizes and strengthens a practice already used by many CASM
fixtures: `tests/fixtures/casm/*.ref.hex` commonly document hand derivation and
are compared to native CASM output with `COMP`. It does not replace those tests
with a second assembler, and it does not accept CASM-generated bytes as an
independent oracle merely because they were transcribed into hex.

No CASM production-language behavior or output format is intentionally changed
by this transition. Native applications may adopt CASM-only syntax later, or in
a separately approved migration increment where a useful conversion is found;
the policy transition itself does not require gratuitous source rewrites.

## Scoping Decisions (user-confirmed 2026-09-01)

1. **Scope covers CASM and all CASM-native external applications.** Tests may
   retain their present implementation when appropriate, but coverage and
   oracle independence must be complete and thorough. DASH is released from
   its load-bearing ca65-compatible source-subset restriction; BANNER and future
   CASM-native applications use the same canonical-oracle policy.
2. **ca65 becomes an optional differential check.** Keep `dash_ref` available
   while the source remains compatible and the check remains useful, but do not
   make it a required build, release, or completion gate. It may cease to build
   after intentional CASM-only syntax adoption without constituting a defect.
3. **Audit and classify every existing CASM `.ref.hex`.** Each reference must
   be classified as independently hand-derived, ca65-derived, CASM-derived, or
   unclear. Circular or unclear references are replaced, independently
   re-derived, or quarantined from authoritative use; none are silently
   grandfathered.
4. **New canonical oracles require derivation plus peer review.** The evidence
   includes annotated byte derivation, source identity/hash, independent
   reviewer/sign-off, and observed machine comparison against native CASM
   output. A tool may validate arithmetic, layout, and metadata, but may not
   derive expected bytes from CASM production tables or CASM output.

## Verification Model

### Authority hierarchy

1. **Normative specification:** documented NMOS 6502/6510 encoding, CASM's
   documented language semantics, PRG framing, and Command 64 R6 format.
2. **Canonical oracle:** independently derived expected bytes and structural
   metadata reviewed without consulting CASM output or CASM production tables
   as the derivation source.
3. **Native observation:** CASM running under Command64 in VICE or on hardware,
   assembled output compared byte-for-byte with the canonical oracle.
4. **Optional differential evidence:** ca65 or another assembler, only when the
   exact source semantics overlap. A mismatch is investigated and classified;
   it does not automatically make CASM wrong.
5. **Determinism evidence:** repeated native CASM runs compare identically. This
   detects instability but is never a substitute for an independent oracle.

### Oracle classes

| Class | Required evidence |
| --- | --- |
| Static PRG | Load address, address ledger, opcode/operand or directive-byte derivation, byte count, SHA-256, source SHA-256, reviewer sign-off, live `COMP` |
| R6 PRG | Static evidence plus relocation eligibility ledger, sorted entry offsets, count/terminator/footer derivation, relocation application at multiple bases |
| Repetitive/large output | Reviewed seed bytes and count/range formula, independently expanded by generic tooling, total length/hash, boundary spot-checks, live `COMP` |
| Diagnostic rejection | Exact diagnostic identity/location and proof that no committed output exists; no fabricated `.ref.hex` |
| Listing/map | Canonical text/record layout where output is contractual, otherwise focused structural harness plus rationale; never infer correctness from PRG identity alone |
| Determinism-only | Explicitly labelled non-oracle evidence and paired with an applicable canonical or structural test elsewhere |
| Native application manifest | Reviewed native artifact, source hashes, independent byte/relocation derivation record, reviewer sign-off, runtime evidence; optional differential note clearly non-authoritative |

### Provenance states

The audit register must assign exactly one state to every reference:

- `CANONICAL-INDEPENDENT`: derivation and review satisfy the new contract.
- `DIFFERENTIAL-ONLY`: useful output from ca65 or another assembler, never the
  authoritative expected bytes.
- `NATIVE-OBSERVATION`: CASM-produced evidence or shipping bytes, useful for
  reproducibility but circular as a correctness oracle.
- `UNCLEAR`: provenance cannot be established from repository evidence.
- `NOT-APPLICABLE`: failure/structural/determinism case for which fixed bytes
  are not the correct assertion.

Only `CANONICAL-INDEPENDENT` may be packaged as an authoritative `.ref` for
native `COMP`. An `UNCLEAR` item blocks completion until it is re-derived or
removed from authoritative use.

## Audit and Remediation Method

The inventory is generated from repository files, then reviewed manually; the
inventory generator may inspect metadata and relationships but may not decide
that bytes are correct. The checked-in audit register records at least:

- oracle/reference path and corresponding source fixture(s);
- feature and output class;
- current byte count and hash;
- git state (tracked, untracked, or modified) and active-WP owner;
- `CASM_REF_NAMES` membership, build output path, every packaging image, and
  generic packaging-loop exclusion reason;
- current claimed provenance with citation;
- actual producer path in CMake/scripts;
- complete source set, including multi-root, include, and payload dependencies;
- generator identity plus a deterministic hash of exact generated `.seq` bytes;
- source-hash and artifact-hash status;
- D64 target and native invocation/comparison command;
- provenance state;
- missing derivation/review evidence;
- remediation disposition, reviewer record, historical evidence paths, and
  re-audit trigger.

For generated fixtures, a hash of `GenerateCasmTestFixtures.cmake` alone is
insufficient: unrelated edits would stale every fixture, while no generated-
source hash cannot prove correspondence. Record both generator identity and a
deterministic hash of the exact generated source bytes consumed by CASM.

For each non-canonical authoritative reference, remediation follows this order:

1. Reconstruct expected bytes from public instruction/output specifications and
   source semantics without reading CASM output as the answer.
2. Have a second reviewer reconcile addresses, encodings, lengths, hashes, and
   R6 entries against the derivation.
3. Compare the newly frozen oracle to native CASM under Command64.
4. If native bytes differ, stop and classify the mismatch before changing
   either side.
5. Preserve the old reference only as labelled historical/differential evidence
   when it adds value; otherwise remove it from authoritative packaging.

The audit also builds a feature-to-evidence matrix covering all documented
opcodes/addressing modes, branches, constants/expressions, directives,
multi-file/include behavior, local labels, static output, R6 output, listings,
maps, diagnostics, deterministic replay, and production native applications.
Missing coverage becomes an explicit follow-up or, with user approval in the
relevant WP, a new fixture on a capacity-appropriate dedicated test image.

## Native Application Transition

The generic native-application contract in `src/external/AGENTS.md` becomes:

- CASM-native source follows documented CASM syntax, not a ca65 intersection.
- The checked-in shipping manifest remains native-observation provenance and
  stale-artifact protection, while an independent derivation/review record is
  the correctness oracle.
- A ca65 comparison may be recorded as optional differential evidence only.
- Source changes require regenerated native bytes, source hashes, derivation
  reconciliation, peer review, live comparison, and runtime verification.

For DASH specifically:

- Rewrite `src/external/dash/AGENTS.md`'s “Dual-Assembler Subset” as historical
  or optional differential guidance, not a source restriction.
- Keep `dash_ref` as an explicit opt-in target while compatible. It must not be
  `ALL`, required at configure time, a dependency of
  `command64_casm_utils_d64`, or automatically packaged as `dash.ref`.
- Provide an opt-in utility/image path for developers who intentionally request
  the differential check, without making normal CASM/native-app verification
  depend on ca65 compatibility.
- Remove `--allow-host-bytes` as an acceptable normal provenance path. Retain
  `--cross-check` only as optional labelled evidence if it remains useful.
- Establish an independently reviewed DASH R6 derivation record that covers
  load address, program extent, relocation eligibility/exclusions, relocation
  offsets/count, footer, byte count, and hashes. The existing native manifest
  remains the shipped artifact, not proof of its own correctness.
- Update mirrored DASH documentation and release documentation consistently.

BANNER's no-ca65 model remains structurally correct but gains the same explicit
independent derivation/reviewer record; its native manifest alone is not
relabelled as an independent oracle.

## Stop Conditions

- Any active CASM, DASH, diagnostic, native-application, fixture, CMake,
  workflow, or DOX effort changes an audited reference, generated source,
  packaging path, manifest, or governing contract. In particular, do not begin
  WP1 over an uncommitted Phase 15 worktree.
- The worktree is dirty in an oracle-relevant path at baseline time, or a
  reference is untracked, omitted from CMake, or generated from uncommitted
  source.
- An active plan's front matter, body, Taskwarrior state, `brain/task.md`, or
  `wiki/tasks/*.md` materially disagree. Reconcile status before freezing the
  inventory.
- The inventory count does not reconcile exactly among filesystem references,
  generated binaries, CMake packaging, and documented live comparisons.
- An expected-byte derivation consults CASM output, CASM opcode tables, or a
  ca65 binary as its answer rather than as post-derivation comparison evidence.
- A reviewer cannot reproduce the address, byte-count, hash, or relocation
  ledger from the recorded derivation.
- Native CASM differs from a newly approved canonical oracle. Preserve both,
  report first differing offset and structural context, and classify before
  editing production or expected bytes.
- ca65 differs from CASM on shared syntax. Determine whether this is a CASM
  defect, ca65 behavior, source-semantic divergence, or oracle defect; never
  automatically rewrite CASM to match ca65.
- Making `dash_ref` optional accidentally removes ca65 required by another
  application or test target.
- Deferred DASH source work, including the `dvmm.s` renderer/table refactor,
  becomes active while WP2 classification or WP4/WP5 derivation and policy work
  is underway. Stop until DASH source, manifest, relocation ledger, and runtime
  baseline are stable again.
- A manifest source hash changes without an intentional native regeneration
  and review.
- New fixture volume exceeds an existing disk's directory/block headroom;
  stop and use the approved dedicated-image path.
- Any harness/test fails unexpectedly, an approved boundary is exceeded, a
  no-change rebuild changes an artifact, or a genuinely new defect outside the
  active WP is discovered. Default disposition is disclose and defer through a
